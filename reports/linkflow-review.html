03 · 明确的功能错误

A01 · P0选择密码保护，空密码却成功写入

证据：processLinkPassword 在验证前执行 type === 'none' || !password，直接返回 { hash: null }。本地实验已确认 six_digit/custom + 空字符串不报错。跳转与验证接口遇到缺失 hash 又按无密码放行。

建议：先校验类型枚举，只有 none 可返回空 hash；受保护类型必须有有效密码。读取到“受保护但无 hash”的异常记录应拒绝跳转，返回可恢复错误。

回归：通过 API、Action、更新密码分别提交空密码、未知类型、非六位数字；均不得产生公开保护链接。修复已有异常数据前先备份与统计。

A02 · P1Server Action 丢弃密码校验错误

证据：createLink 内部只提取 result.hash，没有检查 result.error。因此不合规密码可能作为空 hash 写入；/api/shorten 则检查错误，两个入口行为不同。

建议：写入前调用并检查一次 passwordResult；失败时立即返回统一错误结果。不要在 insert 对象中隐藏异步 IIFE。

A03 · P1首页显示有效期选项，却没有提交有效期

证据：ShortenForm 没有 expiresAt 状态，也没有向 LinkFormFields 传 setExpiresAt；JSON 请求不包含 expiresAt。用户选择 1 小时、7 天或永不过期，不影响最终 API 请求。

建议：创建入口共享完整表单模型，确保有效期字段参与提交。用显式模式表达 default / permanent / duration，避免 undefined 同时表示“默认”和“永久”。

A04 · P1默认过期时间和永久模式没有统一契约

证据：API 缺 expiresAt 会应用 defaultExpiration；Action 缺 expiresAt 直接写 null。API 中“永久”若提交空值，也会回退到站点默认。Action 直接调用则可绕过默认时长。

建议：服务端共享有效期解析器；明确区分未提供、永久、相对时长、绝对时间，并拒绝无效或已过期时间。基于创建时刻计算时长，避免在表单打开时提前消耗有效期。

B05 · P1自定义口令 128 字符与 bcrypt 72 字节不匹配
